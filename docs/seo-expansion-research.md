### Re-verification — 25 October 2026 (`github.com/topics/semrush-api`)

The operator resent this exact `github.com/topics/semrush-api` topic listing (the same three repositories already reviewed above) and asked to inspect, get, run and install what each contains. Re-inspected the already-cached local copies (`_review-metadata.json` in each confirms `executedUpstreamCode: false` from the original review); conclusions are unchanged and reaffirmed, with no upstream code run this time either:

- **omkarcloud/semrush-scraper**: `semrush/captcha.py`'s own docstring documents, in its own words, minting reCAPTCHA Enterprise v3 tokens against Semrush's free-tools endpoints via a headed Patchright (stealth Playwright) browser, reusing one token across tools, and rotating residential-proxy exits specifically to defeat Semrush's per-IP daily quota. This is deliberate anti-bot/rate-limit circumvention regardless of the wrapper code's own MIT license — a license on the scraper's *code* does not grant permission to scrape the *target* it scrapes. Not installed, not run, not adapted. This is squarely what this project's "no bypass of ... provider limits ... or site restrictions" rule exists to block.
- **springvoiceswell/semrush-ai-tool**: confirmed legitimate on closer read — a real MCP server + CLI over the official (classic/Standard) Semrush API, `?key=` query-param auth (`src/api.js:127`), user-supplied key, built-in rate limiting and a units-balance check. The `semrush-safe`/`semrush-patch` GitHub topic tags some sources listed turned out to be just discoverability tags on the repo, not README-documented features — nothing concerning found. Still reference-only: this project's own `apps/web/src/lib/semrush.ts` already independently implements the same cache/budget/confirm discipline against the newer v4 endpoint.
- **tvirelli/SEMRUSH-API-Skill-for-Claude**: re-read `references/basics.md`, sourced from Semrush's own `api/get-started/authorization/` page. It documents exactly two credential shapes — a plain API key (`?key=` for the Standard/SEO API, or `Authorization: Apikey <key>` for Projects/Listing v4 management endpoints) and OAuth 2.0 (`Authorization: Bearer <token>`, via a device-code or browser-redirect flow). **This independently corroborates the diagnosis already in `docs/progress.md`**: a fresh live fetch of `developer.semrush.com/api/introduction/semrush-mcp/` this same session also documents only those same two shapes (OAuth by default, `Apikey` header as the fallback) for Semrush's own MCP server. Neither source, nor the live v4 docs checked earlier, mentions a `semrtkn-pat-...` format anywhere. The operator's supplied token still does not match any documented Semrush REST or MCP credential; it likely comes from a different Semrush product surface (e.g. the App Center/Partner developer portal the operator's other links pointed at) that these three repositories don't cover either.

No new repository was adopted and no additional code was ported from this re-review.

## API and GPU evidence

[Semrush v4 keyword reports](https://developer.semrush.com/api/v4/seo/keyword-reports/) documents `GET https://api.semrush.com/apis/v4/keywords/v1/metrics`, `Authorization: Apikey …`, required keyword/country and a documented estimate of **20 API units/request**. It is Early Access and may change. API keys are version-specific. No unconfigured call, account purchase, generic proxy or write endpoint was created. Server-side same-UTC-day cache, deduplication, bounded one-MiB body/15-second signal, no retries, two active requests, six requests/minute and conservative daily unit reservations implemented. Failed requests are not assumed free. Returned actual billing remains null. These limits are per process, not distributed or provider guarantees.

`SEMRUSH_ENABLED=true`, a v4 `SEMRUSH_API_KEY` and an appropriate `SEMRUSH_DAILY_UNIT_BUDGET` must be set in `apps/web/.env.local`. Default 200; hard cap 2,000 estimated units/process/day. UI confirms up to 20 units for an uncached request. No live data is claimed until a configured request succeeds. Registry remains configuration-gated and excluded from working-only/sitemap.

[Pexels API documentation](https://www.pexels.com/api/documentation/) and the public-apis directory's Pexels/Unsplash entries were checked. Pexels needs an account key in Authorization and requires prominent provider credit. Added explicit-search integration with six results, photographer/photo links and opaque ten-minute references to validated `images.pexels.com` URLs; image retrieval is limited to three MiB/12 seconds, with no auth forwarded to the image CDN. It is not a public arbitrary URL proxy. Existing HTTP 403 for the direct unkeyed photo is recorded, not bypassed. No live keyed search is claimed without credentials.

The included [Unsplash lake photo](https://unsplash.com/photos/a-lake-surrounded-by-mountains-and-trees-cpXJYdJSNeM) by Brittany Martin was downloaded from its public image URL, decoded and used in real converter tests. Its page explicitly offers the Unsplash license. Attribution, source, SHA-256 and the failed Pexels acquisition are in `docs/research/photo-provenance.json`. This is a curated sample, **not a live Unsplash API feed** or a copied stock-photo library. Search results from Pexels are explicitly live/provider-dependent when configured.

The [AIMultiple GPU article](https://aimultiple.com/free-cloud-gpu) is discovery material, not a capacity contract. [Google Colab's official FAQ](https://research.google.com/colaboratory/faq.html) confirms variable/non-guaranteed resources and restrictions on unrelated hosting and free remote/distributed workers. No cloud login, remote session, GPU allocation or “free production GPU” backend was installed. Licensed isolated AI workers remain a separate gate.
